# 十二篇全篇整合：分阶段执行与验收

本轮按用户授权处理优先候选表剩余六篇的正式正文、附录及正式补充材料。最新顺序是完成十二篇整体验收，更新记录和第二阶段计划，然后与用户讨论 GitHub 配置。本轮不推送，也不实施第二阶段。第一阶段保持现有阅读布局。根代理负责最终数学验收和发布；两名数学代理负责新篇数学与真实 Lean 证据，结构代理负责集成及软件、浏览器验证。本文件是执行计划，不是完成声明。

每篇在 `corpus/public/reader/<paper_id>/` 交付 `paper-metadata.json`、`inventory.json`、`content.json`、`symbols.json`、`issues.json` 与正式原件。结构代理在文件齐全后将其加入全局显式 manifest；构建器不扫描目录，也不写死论文数。未发表池与本机上传脚本继续忽略，不读取凭据或私稿。

沿用既有数据模型与数学状态：`rewrite_status` 说明正文交付，`rewrite_role` / `proof_scope` 说明证明或范围分析，`statement_assessment` 说明原命题判断，`lean.evidence_role` 区分完整范围定理、部分、反例与无证据。不能改变原命题或假设，也不能因反例编译成功称原命题通过。旧六篇 168 个结果、104 个目标及其中 17 个无 Lean 映射目标保留真实状态；新篇可新增结果，但旧源转录、重写与机器证据不静默替换。

中文与英文覆盖标题、证明正文、条件、定义、范围、符号解释、共享正文及论文适配。翻译只改人读字段；公式、步骤 ID、来源、状态及 Lean 名称/path/行/报告不变。英文空串、中文残留、模板性占位均不能作为已交付。新共享证明使用唯一稳定 ID，在一个责任目录单存完整双语正文；引用者说明全部前提及论文适配。新增字段须先同步结构代理及根代理。

验收依次进行：

1. 对正式元数据与 PDF 核对实际 SHA-256、实际页数；每个源页均有审查记录，跨页原证明与全部编号、未编号推导进入库存。软件只能检查台账结构，独立数学复核由数学代理与根代理承担。
2. 核对库存到结果索引的完整映射及所有来源页、符号、问题、公共依赖的引用闭合；保留重复原文出现和全部目标分母。
3. 严格检查真实正文交付、双语非空覆盖、跨语言保护字段与公式；缺项返给作者补齐，开发预览不得称完成。
4. 验证每个声称通过的 Lean 报告来自成功实际命令，声明类型、公理、源码和 import 闭包哈希当前；定义、辅助声明、部分证明与反例不相加为论文定理数。
5. 核对旧六篇的输入哈希、稳定结果 ID、原文和重写字段及状态；旧报告、原件与历史验收证据保留。通过必要软件回归及公共池隔离检查。
6. 真实浏览器逐一访问十二篇目录、全部结果/公共证明/问题、每个正式来源页、双语、检索、符号入口、Lean 来回跳转与移动布局；另测本地 KaTeX、长证明滚动与大清单性能。报告绑定全部当前构建输入、实现脚本及实际服务快照哈希。
7. 更新 README / STATUS / 数据接口说明，以最终内容的数学边界与验收计数为准；根代理独立验收与 publication 可审阅检查后，先完成记录和第二阶段计划，再讨论 GitHub 配置。结构代理不 stage、commit 或 push。

## 第二阶段：先评估，后实施

本轮仅评估真实用户流程与问题、保存第二阶段计划。方案以“结论 → 适用条件与规范符号 → 证明 → Lean 证据”为主线，收纳原文对照、下载与维护信息等低频动作；命题问题、定义域和未完成证据须在主线明确呈现。不因界面精简隐藏影响正确性的事实。

全库规范符号与公共证明复用由数学代理先检查定义、作用域、基线/空集约定、前提及实际依赖。只有严格对齐的数学关系才能合并；原作者记号与陈述保留。结构代理据数学数据调整界面和查询接口。第二阶段实施等待后续讨论及明确授权，使用用户指定的 gpt-6.1-sol / high；之后才修改界面并重新执行相关验收。
